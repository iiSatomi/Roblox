October 27, offline only. The recovered build `0.26.530` sources establish six ranks and requirements `{200, 200, 200, 210, 220, 230}` (`Config-e0542a83bbf3.lua`), the rank readiness helpers (`Prestige-672f2ceded27.lua`), and `PrestigeAction("prestige")` with exactly one argument (`PrestigeModal-d222227bd456.lua`). The modal explicitly warns that current level becomes 1 and current EXP becomes 0, irreversibly; a positive response reports the new `rank`. These observations do not establish that Inventory, Crew, Cash, skills or other account fields reset, and this component makes no such claim. The native reserve/excess helpers are outside this transition's confirmation claim.

`PrestigeState` now exposes finite current `xp`, `xpKnown` and a level/EXP/rank `preview` string. Legacy fixtures without EXP can still display readiness, but cannot propose a reset. A reader instance pins all six level thresholds and the catalog fingerprint/release; changed thresholds under an unchanged fingerprint are refused. `PrestigeTab:Preview(snapshot, context)` returns this current source-bound view. The tab UI contains the known irreversible effect and three typed scalar preferences: `allowReset=false`, `targetRank=6` (1–6) and `maxResets=0` (0–6); the feature switch also defaults off. The UI names the missing controller/durable-usage owner rather than asking again for coding permission. Current client display and ownership remain part of shared integration.

`PrestigeReset.new(currentReader)` owns the tightly coupled `propose`, `capture` and `evaluate` functions; static `PrestigeReset.describe(proposal)` supplies the native call description. The tab uses it only when the optional module is injected, preserving the blocked fallback for older callers. `NativeCallPlan.withPrestige(base, PrestigeReset)` and optional RuntimeHost binding delegate this feature to its domain description. No new independent sender, timer or local counter was introduced.

A reset requires current readiness, known EXP, explicit reset choice, current rank below the selected target and `attempted < maxResets`. The raw snapshot must have `prestigeUsageProof` with matching `session/account/place/release/revision/capturedAt`, an integer `attempted` from 0–6, and `controllersClear=true`. The future shared owner supplies actual native progression-controller arbitration and durable sent-attempt usage, including unconfirmed requests. Missing, stale or malformed proof cannot become an assumed zero/clear state.

The flat proposal retains the original rank, next rank, level, EXP, catalog key/requirement and selected limits/usage. Its stable action key is `prestige:<rank>:<nextRank>`; resources are empty. Send-time capture reruns the exact source reader/planner and rejects changed progression, source, usage, controller clearance, limits or resource exposure. Confirmation needs the matching positive non-pending/non-rate-limited reply's `rank` and a newer same-scope complete Sync with exactly `prestige+1`, `level=1`, `xp=0`. A reply alone, manual state change without a matching reply, wrong rank, old scope or stale revision remains pending. Unchanged state plus a rejected response remains rejected.
