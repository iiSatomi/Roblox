# Native reuse audit and gear decision

Date: 2026-10-20. Saved client: **0.26.487.1**. Scope: all **55 planned feature controls**, all 50 legacy IDs, six supporting systems and 15 configured pass keys. This updates the recode plan; no gameplay module or paid-access workaround is implemented.

The default is to reuse the game's current operation, rule or controller when it meets the requested scope. Keep a small hub planner only for the user's goal, permission, limits, scheduling and confirmation. Do not rebuild a native operation merely because the legacy script did so.

The [decision register](native-reuse-decisions.json) records every feature, its remaining gap and exact evidence references. Its 80 anchors were checked against the inert extracted source, including normalized source-text SHA-256 fingerprints and one-based extracted-file lines. These are action-surface and rule observations, not a certification of hidden server behavior. Saved server source is unavailable; no live action or ownership test was performed. A release-note claim is labeled separately from client code. No saved source was executed or copied into production modules.

## Gear: native first, one owner

The normal purpose is **keep my best available gear equipped**. Native Auto Equip is a one-shot operation, not evidence of a background equip watcher. The hub should coalesce relevant inventory, roster, equipment and availability changes and invoke the current native operation only when needed. Changing cash or regeneration ticks alone must not trigger it. Suppress repeated no-op calls until relevant inputs change.

Use one loadout owner. The local design preview now makes `crew` (native) and `crewGear` (custom) mutually exclusive. Selecting one clears the other; turning one off does not secretly start the other. A profile containing both true values is rejected atomically. This is local UI-state behavior only; actual Ember bindings and runtime ownership follow later.

Native is the preferred engine when equip is deliberately enabled, not permission to turn it on at first launch. Migration must show existing non-default attack/defense goals, copy exclusions and Collection priorities that native scope cannot faithfully represent. Preserve those intents in an inactive import for review instead of silently replacing them with the native strongest-gear objective.

Native scope still needs a bounded verification slice before production enablement:

1. Confirm exact player and Crew equipment after one authorized operation, including the native changed/no-change cases. A successful reply alone is insufficient.
2. Compare two-piece and three-piece sets, upgraded variants, bound/unbound copies, duplicate copies and uneven player/Crew allocation. The release notes do not expose the optimizer's objective or prove global optimality.
3. Verify how it treats Collection custody and bonuses, training, recovering members and hub-reserved or user-excluded gear. Only stationed and auto-rolling preservation is stated in the observed UI message. Do not generalize that message into every protection.
4. Because the observed button sends no filter payload, do not claim it can enforce arbitrary hub exclusions. If an active reservation cannot be honored, postpone or use a separately validated constrained route; do not call it and blindly undo unexpected changes afterward.
5. Reconcile stable member IDs after sorting/hiring/station changes. Coordinate gear with Collection, Market and other item consumers. One automatic sender owns each gear transaction and its uncertainty record.
6. Test a second unchanged invocation, interrupted/stale state, late proof and disable/unload. Preserve the existing 45-second unconfirmed rule without repeatedly replaying an uncertain equip.

Only add custom execution for a demonstrated objective the native operation cannot express: for example, an explicit attack/defense preference, a protected-copy constraint or a Collection allocation goal. These are candidate gaps, not established omissions. Compare the same eligible inventory and reservations, include set/Collection effects and reachable transaction costs, and show the result honestly. Do not promise a stronger or globally optimal loadout. Preserve capability through a small optional policy, not dozens of scoring weights or a second default equip loop. Cosmetic background/border optimization remains separate until native coverage is demonstrated.

## Owned controllers and ordinary-action alternatives

| Native controller | What is already present | Remaining compatibility question |
| --- | --- | --- |
| Auto Jobs | Selected Job, mastery, XP/cash modes, proportional energy reserve and refill choices | Can it express the requested absolute reserve, Heists/Favors priority and Contract goal without competing for resources? |
| Auto Buy | Item kinds, rarity floor, only-new, cash/Gold/both, Gold reserve and out-of-funds behavior | A Gold reserve does not supply a cash reserve, selected-item budget or total spend cap. Delegate only a policy it can actually honor. |
| Auto Roll | Empty slots and all-below-rarity scope, selected tier/target | Can it preserve trained/protected members and the user's funded replacement limits? Do not start broad scope on that assumption. |
| City Boss Auto | Progression between eligible stages and chosen refills; saved auto-run state | Compare health, stamina, attempt caps and item permissions. This is not a Global Boss, Takedown or PvP controller. |

Ownership and activity are different facts. Observed examples include `derived.autoJobs` versus `autoJob`, `derived.autoRoll` versus `autoRolls`, and `derived.autoBoss` versus `bossStage.auto`; these still need current-shape validation. Native Auto Buy ownership alone also does not establish that buying is active. Unknown activity state is a compatibility blocker, not proof that the native owner is stopped.

Native controllers run outside the hub broker. When the game owns an activity, show that status and yield affected hub work. Do not silently stop/reconfigure a native run or assert the hub's one-request gate, one-second spacing, reserves or 45-second request deadline constrain every later native action. Attribute external resource changes separately and recheck resource competition with unrelated routines.

## Gamepasses and legitimate alternatives

The snapshot config lists 15 pass keys. No client-side ownership edit, removed check, spoofed flag, altered paid-action mode, fabricated voucher or free entitlement is part of this design.

| Pass group | Recode treatment |
| --- | --- |
| `autoJobs`, `autoBuy`, `autoRoll`, `autoBoss` | Use the native controller only when owned and compatible. Otherwise retain independent automation of ordinary actions available to the account, with normal costs, unlocks, cooldowns and limits. This does not unlock the paid controller. |
| `marketShop` | The native UI also supports timed rental with owned Gold. Keep that separate opt-in, native price and rent-attempt cap. Rental costs in-game currency and does not grant permanent pass ownership. |
| `offlineOperations`, `fourthSlot` | Respect actual offline/slot entitlements. An online scheduler does not run while the client is closed or unlock an extra slot. |
| `vip`, `regenEnergy`, `regenStamina`, `regenHealth`, `noBankFees`, `doubleJobIncome`, `doublePropertyIncome`, `luckyHire` | Read current server-derived benefits. Automation cannot supply their privileged stats, rates, fees, reward multipliers, access or odds. Ordinary resource use is not a free version of those benefits. |
| Existing legitimate pass vouchers | The game has pass-voucher definitions and native redemption for owned items. An actually owned eligible voucher is a legitimate route, not an entitlement bypass or proof that vouchers are free. Do not automatically buy, trade, gift or consume one as part of this audit. |
